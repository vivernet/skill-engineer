# Проектирование навыков: набор инженерных паттернов

## Выбор правильной единицы абстракции

| Задача | Решение |
|---|---|
| Один раз изменить исходный код | Обычная задача, не навык |
| Конкретное правило только одного проекта | AGENTS.md/локальный стандарт |
| Повторяемый порядок принятия решений | Skill |
| Нужна детерминированная трансформация | Скрипт или инструмент; Skill — инструкция его применения |
| Нужны собственные события, постоянное соединение, сложная авторизация | MCP/tool/plugin + Skill как обёртка |
| Большой справочник | Тонкий SKILL.md + тематические references/ |

## Discovery

1. Найди действующий процесс, который нужно **повторяемо улучшить**. Уточни конкретный наблюдаемый результат и допустимые ошибки.
2. Изложи «контракт»: вход, выход, предпосылки, разрешённые действия, явные запреты, условия остановки, обработка ошибок.
3. Составь примеры срабатывания и несрабатывания. Не путай название проекта с сигналами активации.
4. Определи тип навыка: дисциплина (правило), техника (метод), паттерн (выбор), справочник (доступ к знаниям), интеграция (внешние API/CLI/MCP).
5. Заранее спроектируй тесты; они являются спецификацией успешного поведения.

При проектировании используй также эти приёмы:

- Сначала ищи ответы в запросе, существующем навыке и доступных материалах. Обычные обратимые решения принимай самостоятельно и обозначай допущения; уточняй существенные для результата неизвестные, когда нельзя обоснованно принять решение самостоятельно.
- Для значимого выбора сопоставь подходящие варианты по целям, ограничениям и рискам, затем обоснуй выбор. Если подходит только один вариант, не придумывай альтернативы ради количества. Отличай решение пользователя от своего предложения.
- Наряду с ожидаемым результатом опиши существенный нежелательный результат и включи его в критерии или отрицательный сценарий. Например, тест обновления навыка должен проверять сохранность чужих изменений, а не только успешное изменение файла.

## Frontmatter и активация

Используй `name` и `description`. Имя: `^[a-z0-9]+(?:-[a-z0-9]+)*$`, длина до 64 символов, точное совпадение с папкой. Описание до 1024 символов, максимально конкретное, со словами пользователя и условиями использования. Хороший шаблон:

`description: Use when creating or auditing an Agent Skills SKILL.md, debugging incorrect skill triggering, or converting an MCP tool workflow into a reusable agent skill.`

Описание **указывает когда и для чего**, но не заменяет чтение полного SKILL.md. Не добавляй в описание десятки общих ключевых слов для искусственного срабатывания.

Выбирай язык описания по пользователям и сценариям; английский не обязателен. Статический валидатор проверяет наличие и длину `description`, но не может надёжно определить по отдельным словам, ясно ли описаны условия применения. Проверяй смысл и положительные/отрицательные примеры отдельно.

## Progressive disclosure (OpenAI + Gemini)

- `SKILL.md`: минимум для правильного запуска и безопасного результата, ссылки на точечные документы.
- `references/`: стандарты, углублённые рецепты, спецификации конкретных API, режимы.
- `scripts/`: процедуры, для которых опасна вариативность человеческого языка; обязательно тесты.
- `assets/`: примеры/шаблоны/схемы данных, реально нужные по задаче.
- Отдельные файлы — ради экономии контекста и поддержки, а не чтобы раздуть объём.
- Указывай в SKILL.md, **когда** открыть каждый reference. Не прячь обязательные запреты глубже первого файла.
- Проверяй относительные пути/ссылки и запускай скрипты через интерпретатор.

## Степени свободы (OpenAI)

- High: вопросы дизайна с несколькими разумными ответами — принципы, эвристики, критерии.
- Medium: проверенные шаблоны с параметрами — план плюс способы адаптации.
- Low: удаление данных, операции с учётными записями, платежи, миграции — точная последовательность и код с валидацией.
- Ставь проверку перед потенциально необратимой операцией; пропиши предварительный просмотр и явное согласие пользователя.

## Композиция сложных навыков (Skill Forge)

- Делай автономный **фасад**: пользователь вызывает один понятный навык, а внутри находятся небольшие подзадачи и локальные проверенные ресурсы.
- Не полагайся на принудительное вызвание сторонних навыков. Если внешняя реализация опционально установлена, использование возможно только после проверки разрешений и совместимости; отсутствие не должно ломать основной workflow.
- Ограничивай вложенность references одним уровнем для простого обнаружения.
- При росте ответственности разделяй независимые навыки, а не создавай гигантский скрипт с неуправляемыми эффектами.
- Все субагенты должны иметь чёткий input/output и право работы только со своей областью. Если есть параллельные субагенты, исключай гонки записи.

## Категории тестов

| Тип | Поведенческие проверки |
|---|---|
| Discipline | давления, рационализации и обход правил |
| Technique | корректное применение к новым примерам, границы |
| Pattern | распознавание применимости и неприменимости |
| Reference | поиск правильного факта и корректное использование |
| Integration | авторизация, таймаут, rate limit, ошибка сети, идемпотентность |

## Антипаттерны

- Пишем длинную историю разработки вместо применимых правил.
- Дублируем материал системного промпта.
- Вместо тестирования агента делаем grep по SKILL.md.
- Создаём 10 почти идентичных примеров для разных языков.
- Добавляем скрытые требования, не указанные в frontmatter.
- Копируем чужие навыки с лицензиями и зависимостями без проверки.
- Указываем сторонний tool как обязательный без проверки его наличия.
